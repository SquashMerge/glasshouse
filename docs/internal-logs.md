# Internal operational logs

Settings → Logs lets an Organization Admin inspect retained Glasshouse API operational records without access to a host filesystem, Docker socket, container runtime, or Docker's rotated log files. It is not the user-action audit trail.

## Source and trust boundary

The only shipped source is `api`. After an authenticated request in a static allowlist of `/v1` route groups completes, the API stores a record for that request's server-derived Organization: timestamp, severity derived from the response status, a fixed route-group name, HTTP method, status, and duration. Reads of the logs endpoint itself are excluded so paging cannot evict its own results. Source and message are fixed values. Request IDs, request bodies, headers, cookies, authorization values, prompts, telemetry payloads, query strings, and user-supplied route content are never placed in the collection record. The collector accepts only those primitive allowlisted fields before it queues an insert.

Records have a required `organization_id`; `GET /v1/admin/logs` derives that scope from trusted authentication and requires current `organization_manage` authority. An Admin can never select another Organization or retrieve instance-wide records. Unscoped process startup, host/container, database, worker, and Docker runtime logs are intentionally not collected or shown. Operators remain responsible for those sources through their normal deployment tooling.

## Retention and availability

Collection is enabled by default. Set `GLASSHOUSE_INTERNAL_LOGS_ENABLED=false` to disable it; the API then returns a source-unavailable response and the UI exposes a retry state. A failed insert or full queue also marks the local process's collector unavailable and emits a content-free `internal_logs.collection_failed` warning. A later successful insert restores local availability, but lost entries are not recovered. Availability is per API process: a request routed to another replica can still report available, and a restart resets the indicator. It is not an aggregate health or completeness guarantee. Enabling collection begins collecting new records only; it does not import historical stdout or rotated Docker logs.

Rows are visible for at most 14 days and capped at 50,000 rows per Organization. Every read enforces the 14-day cutoff. Each collection transaction takes its Organization's transaction-scoped advisory lock before inserting and removes up to 1,000 over-cap rows before it commits, so concurrent API replicas cannot race an insert against a stale trim. Every API process also runs an hourly, transaction-lock-coordinated cleanup that deletes up to 1,000 expired rows, so cleanup continues even when an Organization is inactive and only one process works on a batch. The maintenance timer does not keep a shutting-down API process alive; an interrupted transaction rolls back and another process resumes later. The physical deletion backlog can lag if the API is down, the database is unavailable, or more than one batch is overdue; the query cutoff still prevents expired rows from being returned. This is a bounded in-product store, not an archival logging system; high traffic can evict newer-than-14-day records once the row cap is reached. Database unavailability can prevent collection or cleanup, so absence of an entry is not proof that an event did not occur.

## Query behavior

`GET /v1/admin/logs` accepts a time range, level, source, and free-text query. The first page fixes the matching rows visible to one PostgreSQL statement, ordered by `recorded_at DESC, id DESC` (including timestamp ties). Entries committed after that statement are not included, even when their timestamps sort between existing entries. Use **Refresh** for a new traversal. The page loads further results on scroll and has a keyboard-accessible **Load more logs** button.

PostgreSQL stores only ordered identifiers and timestamp sort keys, not copies of log payloads; the snapshot is shared between API replicas. Each page rechecks current Admin authority and verifies the snapshot rows remain present, correctly scoped, unexpired and at their original sort keys, in the same database read as the page. If retention, expiry, changed keys, a different Actor/Organization/filter, or a malformed or altered cursor invalidates the traversal, the API returns `409 CONFLICT` with a refresh/restart message; no incomplete page is returned. Authorization loss returns `403`. Removing the Admin role invalidates that Actor's snapshots, so regranting access requires a new traversal. Total is fixed for the traversal. The endpoint does not promise uninterrupted traversal when retention removes rows.

Each snapshot expires after five minutes and is removed on a later allocation or by hourly maintenance. Single-page snapshots are removed immediately because they have no continuation cursor. Multi-page snapshots remain until expiry so a lost final-page response can be retried. An individual snapshot is bounded to 50,000 identifiers and 1,250,000 bytes of identifier/sort-key arrays. Allocation is serialized across replicas and capped at eight active snapshots per Actor across Organizations, 32 per Organization, and 128 globally. A full quota or oversized matching set returns `503`; retry after capacity expires or narrow the filters. Limits do not make this an archival store, and inactive expired rows can remain physically present until cleanup.

The page presents only safe persisted context. Selecting a row opens its JSON context; it cannot reveal data removed during collection.
