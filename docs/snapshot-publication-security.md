# Private snapshot publication: disabled pending live security validation

`.github/workflows/snapshot-publish.yml` and `scripts/snapshot_ghcr.py` implement a GHCR publisher in this public repository, but **it is disabled by default and must remain disabled until the checks below are satisfied**. No packages, secrets, permissions, tags or releases were created by this work. An authorized organization-admin package listing was reported empty, with both intended package metadata endpoints returning 404; the required bootstrap has not been performed. The proposed packages are `ghcr.io/squashmerge/glasshouse-api-snapshot` and `ghcr.io/squashmerge/glasshouse-web-snapshot`; only `linux/amd64` is targeted.

## Before enabling

1. An organization administrator must establish both packages with **private** visibility before any application image is pushed. Bootstrap each package with an independently reviewed harmless image under tag `bootstrap`, using a controlled administrator workflow. Confirm the exact package names, organization, creation policy, inheritance, Actions access and package writer permissions. The publisher will not create an absent package or assume that a 404 means private.
2. Review private package exposure to public-repository Actions and fork PRs, effective read/write access, trusted main protections, and the ability to restrict writers to this workflow and necessary administrators. Test authenticated operator and workflow pulls and explicit anonymous pull denial. A private package visibility field is **not** proof of these policies. Record the review outside this repository, and set `SNAPSHOT_PACKAGE_POLICY_REVIEWED=true` only if the review establishes an acceptable boundary. This variable is an operator assertion, not an automated policy verifier. The `GITHUB_TOKEN` must be able to query organization package metadata and pull and push both packages; this has not been demonstrated. GitHub documents token requirements differently for organization package REST metadata and Actions package management; compatibility of this exact metadata endpoint with this workflow token is unverified. If it cannot access the endpoint, fail closed; do not add a PAT or secret as a workaround without separate security review.
3. Independently review and validate the workflow and its pinned Actions, and run a controlled end-to-end test with private throwaway packages using an explicitly authorized procedure. Confirm digest preservation by Skopeo, anonymous-denial and authenticated-read probes, reservation writes, retries and the image integration test. The existing code hardcodes the production names; do not change them and accidentally test against production. No real registry push has been performed here.
4. Keep publication disabled until the other prerequisites and a controlled private-registry end-to-end test pass. Set `SNAPSHOT_PUBLISH_ANCHOR` to the full lowercase SHA of the last **excluded** main first-parent revision immediately before enablement, and preserve it. After confirming there has never been a checkpoint or publication, enable the workflow and manually dispatch it once with `initialize_checkpoint` checked; that dispatch creates the checkpoint only and publishes no revisions. Normal dispatches must leave it unchecked. A missing checkpoint later is an incident: do not initialize again or guess a cursor; restore an independently preserved, verified checkpoint and reconcile its registry records under a reviewed procedure. Protect branch, workflow, variables, package settings, checkpoint and all records against unauthorized writes or rollback. Revoke the enable variable to stop new runs, and separately cancel any active run if necessary.

The source repo is public. The publisher does not upload records or SBOMs as Actions artifacts. It keeps the durable compressed SBOMs and gate/digest/checkpoint records in the private API package, and suppresses build and integration output. Actions metadata and other workflow logs are not a private evidence store; do not publish records in logs or artifacts. Privacy and the absence of unintended disclosures require a live review.

## Admission and reconciliation

The publisher responds to successful trusted `push` workflow completions and to scheduled/manual reconciliation. The event is only a wake-up. A private OCI checkpoint records an exclusive anchor, a first-parent cursor and an ordered pending backlog. Each run admits at most five new revisions to the backlog and attempts at most ten pending revisions, rotating blocked items so neither backlog nor new commits are silently skipped. Every checkpoint advancement is written and read back before those revisions are processed. Workflow-run/job pagination has a 400-request process budget; other API calls and other concurrent workflows also consume GitHub's shared rate limit, so rate limiting may delay progress. Repeated scheduled/manual runs are necessary when the queue is long. Missing, malformed, mismatched or unexpectedly changed checkpoints fail closed. No checkpoint-based algorithm protects against an authorized writer maliciously replacing, deleting or rolling back its state.

The runner refreshes the first-parent chain before reservation and image writes; a failed fetch blocks publication rather than using cached refs. This assumes the configured origin is trusted and cannot make the ref check atomic with a registry write, so protect main against force pushes. Each revision must have both exact-SHA trusted `push` workflow runs on `main`, with successful latest run/attempt and the complete expected successful job set. Missing, cancelled, failed, in-progress, PR or mismatched checks do not pass. See `scripts/snapshot_admission.py` for the pinned job contract. A rerun of failed jobs can omit successful jobs from the attempt; rerun **all** jobs on the original trusted push run. Multi-commit push revisions lacking separate runs remain pending; they are not silently treated as tested by the tip. If live evidence expires before an incomplete revision is published, it remains blocked. A fully reserved pair with matching registry tags can be recovered without querying expired CI only after validating the stored trusted-writer gate evidence, repository, package names, SHA and both image digests and refreshing main.

Publishing is serialized with GitHub's `queue: max`, `cancel-in-progress: false`. The queue is bounded at 100 pending runs; overflow, manual cancellation, Actions downtime and job timeout remain possible. Scheduled and manual reconciliation continue from the private checkpoint and retry the backlog. Logs report blocked status without revision details; inspect the private checkpoint under authorized access for pending SHAs. Monitor failing/cancelled runs. The workflow uses main checkout and refuses PR triggers; no third-party action is unpinned. `GITHUB_TOKEN` is passed through the environment/stdin, not command arguments, and is removed from build/test child environments. Package permissions are granted only to the publisher job.

## Candidate, records and retry

For each admitted SHA not already represented by a matching reserved pair, the runner makes one tracked `git archive`, builds the API and web OCI candidates from that archive, checks their manifest and configuration digests, loads them into Docker, scans the actual loaded images with Trivy for HIGH/CRITICAL fixed vulnerabilities and secrets, and generates CycloneDX SBOMs. It runs the image-only deployment integration against those same loaded image configurations, including migrations, restart, health, authentication and proxy routing. Complete reserved pairs are rechecked by digest without rebuilding; partial pairs require a matching rebuilt candidate. Each target SHA must contain the image integration harness.

Before any app tag is written, the publisher writes an OCI reservation in the private API package, `reservation-<full-SHA>`, containing the source SHA, both manifest digests and raw manifests, platform, gate run/attempts, publisher run and compressed SBOMs. The hash of each stored manifest must match its image digest, and the Trivy CycloneDX root container's `aquasecurity:trivy:ImageID` must match that manifest's config digest (not its manifest digest or an image name). The loaded Docker image config is independently checked against the candidate before scanning. A preexisting reservation must validate and match both rebuilt candidate manifests and digests; an unreserved existing SHA tag or any mismatch fails closed. On a partial retry the publisher requires fresh admission, rebuilds, scans and tests the pair, and validates the newly generated SBOMs, then reuses the original reserved SBOMs and evidence because Trivy regenerates serial numbers and timestamps. The publisher then pushes only missing `<full-SHA>` tags with digest preservation, reads each back, and rechecks the pair and privacy before marking the local run record `complete`. A failure after either push leaves an incomplete reservation and local run record. Do not treat a single tag as a complete pair.

Reservation and checkpoint updates are **not atomic compare-and-swap**. They require exclusive writer control and the serialized workflow; another writer, administrator, registry rollback, or deletion of records and image tags can defeat this protection. Do not delete or retarget reservations, checkpoint or tags. A lost response must be reconciled by reading both exact registry digests; never move a tag to repair an inconsistent pair. A rebuilt candidate often has a different digest and is rejected. The original local OCI archives are not retained between runners, so an interrupted partial publication may need administrator recovery of the exact original candidate; guaranteed automatic repair is not implemented. The reservation is durable while its private registry tag survives, but it alone is intent, not proof of pair completion. It contains compressed CycloneDX SBOMs with a maximum uncompressed size of 8 MiB each and their SHA-256 hashes; oversize SBOMs fail closed. Registry support for records of realistic sizes remains unverified.

The registry record asserts source SHA, publisher run, gate evidence, both image manifest digests and both SBOM hashes and contents. `scripts/snapshot_verify.py` checks the reservation's manifest/config digests, the embedded image manifest hashes and SBOM config identities, its schema and SBOM hashes, both current image-tag digests and fresh first-parent membership, then prints digest-pinned image references and the source. Evidence receives lightweight structural checks: CycloneDX version and root container name, and a single manifest with a config descriptor and a list of layer descriptors, each with media type, SHA-256 digest and nonnegative size. This is not complete CycloneDX or OCI schema validation, nor proof that a registry accepts the artifacts. Earlier records lacking the required evidence fail closed. This is provenance **under the private registry's exclusive-writer trust boundary**, not a cryptographic signature or independent attestation: anyone who can replace the record and tags can forge it. BuildKit attestations are disabled to preserve the single image manifest. Scan outcomes, realistic record size, and registry behavior have not been exercised against real images here. Whether this trust model meets issue #1's provenance requirement needs maintainer review.

For an authorized operator in a checkout configured with the trusted `origin`, authenticated to both private packages, with `gh`, Docker and Skopeo installed and `GH_TOKEN` and `SNAPSHOT_PACKAGE_POLICY_REVIEWED=true` in the environment:

```sh
python3 scripts/snapshot_verify.py <full-source-sha> --sbom-dir /secure/existing-directory
```

The optional SBOM directory must already exist, be private, and contain no same-named files. Output identifies the source, gate run IDs and exact package digest references; keep output private. The verifier is read-only against the registry but writes SBOM files when requested. It depends on the same unverified org-package metadata endpoint as publication. It does not prove a historical record has not been rolled back, establish package permission policy, or make a label independent evidence of the build.

## Read-only tools and tests

`snapshot_preflight.py` is a read-only diagnostic tool that defaults to a no-op. `python3 scripts/snapshot_preflight.py --packages` checks package metadata but does not grant access or publish. `scripts/snapshot_candidate.py` supplies the tracked source archive used by the publisher; it does not independently authenticate source or gates.

The `Snapshot candidate dry run` CI job calls the same `build_test_scan` function as the publisher and is included in its required push-job set. On pull requests it tests GitHub's checked-out merge candidate (`GITHUB_SHA`); on main pushes it tests that push SHA. Its separate archive policy requires the supplied full SHA to equal checked-out HEAD, while publication retains the first-parent archive policy and admission checks. The dry run checks the actual OCI manifest bytes, loaded configuration, revision label and CycloneDX image identity, then runs the same image-only migration, restart, authentication and routing harness. It reports hashes only, not a registry record or signed provenance. It has read-only contents permission, no package permission or secrets, and performs no registry publication or private GHCR package access. It is not network-offline: it downloads public build and runtime images, scanner databases (via the public Google mirror), Actions and dependencies. Neither this job nor the existing image-only integration replaces the controlled private-registry validation required before enablement. A pinned apt package version can disappear from Ubuntu's repositories, requiring a reviewed update to both workflows.

```sh
devcontainer exec --workspace-folder "$(pwd)" python3 -m unittest discover -s scripts -p 'test_snapshot*.py' -v
```
